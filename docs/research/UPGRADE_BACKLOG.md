## 1. 키 하이라이트 재생 모드 (이벤트만 렌더)

- **무엇·왜:** 경기를 **전부 연속 재생**하거나 **즉시 결과**로 건너뛰는 양 극단만 있다. 그 사이 FM식 **"키 하이라이트만"**(첫 교전·설치·해체·클러치·라운드 결정 듀얼만 그리고 나머지는 빨리감기/결과)를 추가. 근거: COMPARABLES §A.1, §D (FM key highlights, FM27은 경기 직후 하이라이트 재생). 엔진은 이미 `eventLog`를 만들므로 선택적 렌더만 추가하면 된다.
- **손댈 곳:** `apps/desktop/src/renderer/matchday/timeline.ts`(이벤트→세그먼트 복원), `screens/matchday/LiveMatch.tsx`·`usePlayback.ts`(재생 모드 상태), `matchday/duels.ts`(교전 구간). 엔진 측 변경 불필요 — `round-simulator`가 내보내는 이벤트를 소비.
- **크기:** M.
- **사용자 체감:** 경기당 소요를 크게 줄이고, 보고 싶은 만큼만 본다(장기 커리어 피로 완화 — 경쟁작 "후반 단조로움" 불만의 직접 해법).
- **저사양 영향:** **강한 양(+).** 렌더하는 PixiJS 프레임 수가 라운드 전체→결정적 구간으로 줄어 가장 약한 PC에서 체감. 저사양 1원칙과 정면으로 부합.
- **우선순위:** P1. **중복:** 신규(§5엔 없음).

## 2. 경기 후 선수 박스스코어 (KAST/ADR/ADRa/FK·FD/멀티킬/클러치)

- **무엇·왜:** 업계 표준 선수 지표가 **입력으론 들어와 있으나**(`docs/research/PLAYER_RATINGS.md`가 VCT Reference에서 KAST·ADR·FK/FD·멀티킬·클러치 사용) **엔진 경기 결과로는 재생산·표시되지 않는다.** 경기 후 VLR식 박스스코어(K/D/A, ACS, ADR, ADRa, KAST%, FK/FD, 멀티킬, 클러치 승)를 선수·팀 단위로 산출. 근거: COMPARABLES §C.3.
- **손댈 곳:** `packages/round-simulator`(`export.ts`/`replay.ts`에 라운드별 킬·생존·트레이드 집계 추가), `packages/combat-engine`(트레이드 창 판정), `apps/desktop/.../ReviewPanel.tsx`·`matchday/duels.ts`(표시), 검증은 `tools/data-validator`.
- **크기:** M.
- **사용자 체감:** 스카우팅·리뷰가 실제 e스포츠 통계처럼 읽힘(신뢰감). 생성 선수 평가의 설득력 상승.
- **저사양 영향:** 거의 없음(경기 후 집계, 렌더 아님). 틱당 추가 비용 없게 이벤트 로그에서 사후 계산.
- **우선순위:** P1. **중복:** 부분 — §5 P2-11은 "데이터가 없어 위치 기반 승률을 못 구함"을 다루지만, 이 항목은 **엔진 산출 지표**라 위치 데이터가 필요 없다(구분해서 진행 가능).

## 3. 라이브 라운드 승률 + 스윙 모먼트

- **무엇·왜:** 관전 중 라운드 승률 곡선과, 경기 후 "가장 승률을 흔든 순간" 표시. `packages/outcome-predictor`가 이미 예측을 하지만 화면에 안 쓰인다. 근거: COMPARABLES §C.2(Xenopoulos XGBoost WP — **장비·HP·인원이 지배적 특징**), §A.2(OOTP 승률 표기). 공간 특징은 그래프 거리로 싸게.
- **손댈 곳:** `packages/outcome-predictor`(`predict.ts` — 라운드 상태→확률, 캘리브레이션), `apps/desktop/.../matchday/timeline.ts`에 WP 트랙 추가, 문서 `docs/research/ROUND_VALUE_MODEL.md`.
- **크기:** M.
- **사용자 체감:** 관전이 "읽히는 드라마"가 됨 — 클러치·스윙이 수치로 보인다. 키 하이라이트(#1) 선택에도 WP 스파이크를 기준으로 쓸 수 있어 시너지.
- **저사양 영향:** **주의 필요.** 추론을 매 틱 돌리면 비용이 든다 → **라운드 상태 변화(킬·설치 등) 때만, 가벼운 로지스틱/GBM로** 계산. 메모리·지연(latency)을 검증 지표에 포함(README §26.4). 끄기 토글 제공.
- **우선순위:** P1. **중복:** 관련 — README §26.3 라운드 가치 모델, HANDOFF §5 P2-9(퀵심 캘리브레이션)과 캘리브레이션 방법 공유.

## 4. 엔진 검증 지표 확장 + 공개 데이터 대조

- **무엇·왜:** 현재 검증은 8–15개 판정 지표(전멸·폭발·해체·공격 승률 등). 여기에 **선수 단위 분포**(KAST·ADRa·FK rate·클러치 승률·멀티킬 빈도)를 더해 **VCT Reference 분포와 대조**. 합법적 1차 소스로 **GRID Riot Open Access**(경제·클러치 확률·픽 분포; 위치는 미제공) 신청 검토. 근거: COMPARABLES §C.1~C.4, 내부 `docs/research/GRID_ACCESS.md`.
- **손댈 곳:** `tools/data-validator/scripts/sim-batch.mts`(지표 추가), `docs/VALIDATION_BASELINES.md`, 대조 데이터는 `vct.duckdb`/VCT Reference. GRID은 신청 후 `datasets/raw/grid/`.
- **크기:** M(GRID 신청·파이프라인 포함 시 상단).
- **사용자 체감:** 간접 — 엔진이 "프로답게" 느껴지는 근거. 리뷰·마케팅에서 신뢰 확보.
- **저사양 영향:** 없음(오프라인 개발 도구).
- **우선순위:** P1. **중복:** 부분 — §5 P2-11과 데이터 출처가 겹침. 단 GRID 신청은 **사용자 판단 사항**(미신청, 베팅 금지·비상업·지연 조건 확인됨).

## 5. 저사양 프리셋 + 지각 틱 O(n²) 완화

- **무엇·왜:** 사용자 1원칙(저사양). **(a) 렌더 프리셋**(2D 전용/3D, FPS 상한, 군중·효과 디테일) + **(b) 시뮬 병목**: 틱당 O(n²) 지각/시야 계산, `routeCache`. 근거: COMPARABLES §A.1·§A.2·§D(FM·OOTP의 디테일 토글), HANDOFF §5 P2-12.
- **손댈 곳:** `apps/desktop/.../matchday/world3d.ts`·`prefs.ts`(렌더 프리셋), `packages/perception-engine`·`packages/spatial-engine`(O(n²)→공간 분할/시야 캐시), `packages/round-simulator`(`routeCache`).
- **크기:** M(렌더 프리셋) / L(엔진 O(n²) 구조 개선).
- **사용자 체감:** 약한 PC에서 끊김 없이 구동. 설정으로 체감 품질/속도 교환.
- **저사양 영향:** **이 항목 자체가 저사양 대책.**
- **우선순위:** P1. **중복:** **중복(§5 P2-12).** 이 백로그는 "렌더 프리셋"을 명시적으로 추가하는 점이 새롭다.

## 7. 미디어·기자회견 + 선수 상호작용→사기

- **무엇·왜:** FM 유지율의 핵심은 **인박스가 만드는 서사**(COMPARABLES §A.1). 우리 커리어 인박스는 풍부하지만 **일방향**이다. (a) 데이터 기반 기자회견/미디어 선택지, (b) 선수 칭찬·질책 등 상호작용이 **사기에 반영**. 사기는 추적되나 경기 반영이 플래그 뒤+효과 미검출(HANDOFF §4 `moraleInMatch`, §5 P2-10).
- **손댈 곳:** `packages/career`(hook API로 미디어 모듈), `packages/career/src/club/board.ts`, `apps/desktop/.../screens/career/InboxScreen.tsx`. 사기→경기는 `readiness`/로스터 경로(이미 존재).
- **크기:** L.
- **사용자 체감:** 장기 커리어의 변주·애착(경쟁작 "후반 단조로움" 해법 2).
- **저사양 영향:** 없음(텍스트·선택지).
- **우선순위:** P2. **중복:** 관련 — §4 `moraleInMatch` 플래그를 "효과 있게" 만드는 작업과 연결(그 자체가 미해결로 표시됨).

## 10. 데이터 에디터 / 모드 지원

- **무엇·왜:** OOTP·FM 장수의 비결은 **커스텀/모드 생태계**(COMPARABLES §A.2·§A.1). 동시에 우리는 **IP 미해결**(HANDOFF §6) — 사용자가 팀·선수·명칭을 직접 넣게 하면 **IP 리스크를 사용자 측으로 넘기고** 독자 세계관 전환도 쉬워진다. 경기 전 에디터 + 데이터는 JSON 스키마.
- **손댈 곳:** `packages/game-data`(스키마·로더), 새 에디터 화면 `apps/desktop/src/renderer/screens/*`, 커리어 월드 생성이 에디터 데이터를 읽도록(`packages/career`), `docs/DATA_SCHEMA.md`.
- **크기:** L.
- **사용자 체감:** 재플레이성·커뮤니티. 실팀 라이선스 없이도 "내 리그".
- **저사양 영향:** 없음(런타임 비용 아님).
- **우선순위:** P2(에디터 최소판) / P3(모드 생태계). **중복:** 관련 — §6 IP 방향 결정과 묶어서 판단.

## 바로 분배할 작업 묶음 (3–5개)

> 각 묶음은 독립 세션 1개가 맡을 수 있게, 파일 경계가 거의 겹치지 않도록 나눔.

- **묶음 A — 관전·가독성(matchday UI 세션):** #1 키 하이라이트 재생 + #3 라이브 승률 + #6 베토 연출. 전부 `apps/desktop/.../matchday`·`series` + `outcome-predictor` 표시층. **저사양에 가장 크게 기여.**
- **묶음 B — 엔진 지표·신뢰(engine-truth/data 세션):** #2 선수 박스스코어 + #4 검증 지표 확장·공개 데이터 대조. `round-simulator`·`combat-engine` 산출 + `tools/data-validator`. 위치 데이터 불필요(#2)와 필요(GRID, 사용자 판단)로 단계 분리.
- **묶음 C — 저사양(spatial/perf 세션):** #5 렌더 프리셋 + 지각 틱 O(n²)/`routeCache`. `perception-engine`·`spatial-engine`·`world3d.ts`. HANDOFF §5 P2-12와 합류.
- **묶음 D — 커리어 깊이(career 세션):** #7 미디어·상호작용→사기 + #8 스카우팅 감쇠 + #9 튜토리얼·난이도. 전부 `packages/career` + 커리어 화면, 엔진 미접촉.
- **묶음 E — 제품·IP(독립):** #10 데이터 에디터 최소판. `game-data`·새 에디터 화면. HANDOFF §6 IP 결정과 함께.

**권장 착수 순서:** 묶음 A(저사양+체감 즉효) → 묶음 B(신뢰) → 묶음 C(저사양 구조) → D → E. 단 A·C는 저사양 원칙상 병렬 우선 가치가 크다.
