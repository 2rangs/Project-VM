## A. 감독 게임 기준점 (장르 원형)

### A.1 Football Manager (FM)

| 항목 | 요약 | 신뢰도 |
|---|---|---|
| 매치 엔진 | 별도 엔진이 경기를 시뮬레이션하고, 2D/3D는 그 결과를 **렌더링**만 한다(엔진과 뷰 분리). FM27에서 **2D 매치 엔진을 다시 강화**한다고 공식 발표. | A |
| 하이라이트 선택 | 전체/핵심(key)/광범위 등 **하이라이트 양을 사용자가 고른다.** "key highlights"는 결정적 순간만 보여주고 나머지는 건너뛴다. FM27은 지난 경기 하이라이트를 경기 종료 직후 다시 볼 수 있게 함. | A/B |
| 저사양 | 최소 사양이 매우 낮음(구형 i3-530 + GTX 960급도 구동). 느릴 때 공식 권장은 **렌더 품질·그림자·군중 품질 낮추기, 60hz 제한**, 2D만 볼 거면 그래픽을 Low로. 단, FM26에서 2D/키 하이라이트 구간이 끊긴다는 포럼 보고 다수. | B/C |
| 스카우팅 안개 | **attribute masking**: 스카우트하기 전엔 능력치가 가려짐. 지식은 **스태프가 보유**하고 스태프가 떠나면 사라진다. 특정 국가 지식은 스카우트 후 약 한 달간 100%였다가 서서히 감쇠. | B |
| 스태프·분석 | 스카우트·코치·분석가·의료진이 각자 지식/능력으로 기여. | B |
| 인박스/뉴스·미디어 | **인박스가 게임의 허브** — 클럽 관련 모든 정보가 뉴스 아이템으로 도착. 기자회견·미디어 상호작용·소셜 피드가 서사를 만든다(팬덤의 핵심). FM25는 인박스를 메인 화면에서 내렸다가 논란. | B |
| 선수 상호작용·사기 | 개별/단체 대화, 팀 토크, 사기(morale)가 경기력과 연결. | B |
| 재정·보드 | 이사회 목표·신뢰, 예산, 이적 자금. | A |
| 시뮬 속도 | "Continue"로 일 단위 진행, 중요한 날에만 멈춤. | A |
| 모드·에디터 | 인게임 에디터 + 대규모 커뮤니티 데이터·스킨 모드 생태계. FM27은 인게임 에디터 복귀 발표. | A |

**우리에게 주는 교훈:** 엔진/뷰 분리는 우리도 이미 지킴(`round-simulator` ↔ `apps/desktop` 렌더). **덜 베낀 것은 "하이라이트 양 선택"과 "인박스가 만드는 서사(미디어·상호작용)"**. 저사양 원칙("사양을 타면 안 됨")은 FM의 반면교사 — FM은 3D·연속 2D에서 사양을 타므로, 우리는 **키 하이라이트만 렌더하는 길**로 가야 한다.

### A.2 Out of the Park Baseball (OOTP)

| 항목 | 요약 | 신뢰도 |
|---|---|---|
| 엔진 성격 | **텍스트 기반** 시뮬. 모든 물리를 계산하지 않고 능력치·분포로 통계적으로 일관된 결과를 낸다. 개발사는 내부 판정식을 공개한 적 없음. | B/C |
| 능력치 근거 | 선수 레이팅을 실제 투영 시스템(ZiPS)·배트 트래킹류 데이터에 기반해 보정. 구장 요인·나이 곡선 반영. | B |
| 저사양·속도 | 성능의 핵심은 **리그 수·규모 줄이기, 통계 상세도 낮추기, 얼굴 생성(facegen) 끄기, 하위 리그 박스스코어/게임로그 저장 줄이기.** 기본값으로 MLB 아래 리그는 박스스코어를 안 남겨서 불만도 있음(상세도와 저장량의 트레이드오프를 사용자가 고른다). | B/C |
| 모드·커스텀 | 가상·역사·커스텀 리그, 커뮤니티 템플릿·에디터로 세계를 직접 구성. | B |

**우리에게 주는 교훈:** "모든 물리를 계산하지 않아도 통계적으로 일관되게"는 우리 엔진 철학과 같다(README §2.2). **핵심은 "상세도를 사용자가 고르게 해서 저사양을 흡수한다"** — 저장량·렌더·시뮬 깊이를 토글로. 우리 커리어의 `world sim depth`(league/quick/full)가 이미 이 패턴이다. 확장 여지는 **경기 관전 상세도**(지금은 라운드 전부 연속 렌더)와 **데이터 에디터**.

## B. e스포츠 감독 게임

### B.1 Teamfight Manager (2021) — MOBA 감독

- **평가:** 매우 긍정적(대략 83%대). "중독성 있고 의외로 깊다"는 평과, **"시뮬·관리 요소가 거의 없다"**는 혹평이 공존. 드라마보다 메커니즘에 집중한 게임이라는 평.
- **장점:** **Pick & Ban(밴픽)**이 가장 호평받는 축. 선수를 세팅해 자동 전투에 내보내는 루프. 가벼운 진입.
- **단점:** 관리 깊이 얕음, 서사 빈약, 자동 전투 관전 연출이 단조로움.
- **신뢰도:** B(전문 리뷰 다수), 세부는 C.

### B.2 Teamfight Manager 2 (2026, 앞서 해보기) — MOBA 감독

- **평가:** 복합적(Mixed, 리뷰 ~2,000건, 긍정 비율 60% 안팎). 원작보다 낮다.
- **장점:** **Team Tactics / Personal Tactics 세분화**로 선수를 "공/수 스탯 묶음"으로만 다루지 않게 됨, 데스매치 모드 추가, **드래프트가 여전히 빛나는 지점**, 창발적 스토리텔링, 개발사 피드백 반응 빠름.
- **반복되는 불만:** **AI 의사결정 품질**(아군이 스로잉·피딩), **메커니즘 설명 불친절(clarity)**, 영입(recruitment) 피로, 버그, **성능·크래시(특히 Steam Deck)**, 튜토리얼 미흡.
- **신뢰도:** 집계 B, 세부 C(애그리게이터 AI 요약 포함).

### B.3 Esports Godfather (2024) — MOBA 감독 카드/덱빌딩

- **평가:** 매우 긍정적(~90%, 리뷰 4,100+).
- **장점:** 드래프트·팀 조합의 전략성, 덱빌딩+팀빌딩+오토배틀+RPG 혼합.
- **단점:** 가파른 학습 곡선·메커니즘 불명확, **후반 그라인딩으로 단조로움**, 특정 버전(1.3.11)의 게임 파괴 버그. **AI 생성 아트(초상·일러스트)** 사용 — 우리 라이선스/윤리 관점에서 반면교사.
- **신뢰도:** 집계 B, 세부 C.

### B.4 Esports Life Tycoon (2019) — 조직 운영 타이쿤

- **평가:** 복합적(리뷰 605). 비평 점수 중위권(6/10대).
- **장점:** 폭넓은 **커스터마이징**(브랜딩·선수), 더 심스식 관계·생활 시뮬 혼합이 "묘하게 중독적".
- **단점:** **금방 질림**(두어 시간), 반복적·얕은 깊이, "e스포츠라는 현상을 제대로 못 담았다"는 평.
- **신뢰도:** B.

### B.5 CS/기타 감독 게임 (라이선스·틈새)

- **CS Manager**(데모/EA), **Esports Manager 2026**(CS2) — **140개+ 팀, 실팀 라이선스**를 전면에 내세움. 실팀 라이선스가 구매 동기.
- **LIGA**(itch.io, CS 시뮬) — "FIFA·FM에서 많이 영향받음", CS 전용·모드 없음.
- **LoL GM** — 레딧발 팬 제작 무료 GM 시뮬(로스터·예산). 팬 커뮤니티가 요구해서 출발.
- **신뢰도:** B/C.

**e스포츠 감독 게임 전반의 교훈(반복 패턴):**
1. **드래프트/밴픽이 가장 사랑받는 순간** — 거의 모든 게임의 호평 축. 우리 밴픽·베토 연출을 키울 가치가 크다.
2. **가장 반복되는 불만은 "불명확함·AI·튜토리얼·버그·성능"** — 콘텐츠보다 **가독성/온보딩/안정성**이 유지율을 가른다.
3. **후반 단조로움(그라인딩)** — 장기 루프에 서사·변주가 필요(FM 인박스가 해법).
4. **실팀 라이선스는 강한 구매 동기지만** 우리는 IP 미해결(HANDOFF §6) → **데이터 에디터/독자 세계관**으로 대체 가치를 만들어야 한다.

## C. 전술 FPS 시뮬·분석 (공개 연구·오픈소스)

### C.1 awpy (오픈소스, CS2 분석)

- Rust 파서(demoparser2 기반) + Python API(Polars DataFrame 반환), Python 3.11+.
- 제공: 라운드·플레이어 상태·틱 샘플링·**궤적(trajectory)**, **ADR·KAST·Rating** 통계, `awpy.visibility`(시야/시선 계산). 승률(win probability)은 알파 버전 기재.
- **우리 관련:** 우리 `replay-engine`·`perception-engine`의 **검증 지표 산출 방식**과 **시야 모듈**의 비교 기준. CS 데이터지만 KAST/ADR/시야 계산 정의가 재사용 가능.
- 신뢰도: A(공식 문서·PyPI).

### C.2 Xenopoulos et al. — "Valuing Player Actions in CS:GO" (arXiv 2011.01324)

- XGBoost **라운드 승률 모델**. 입력: 생존 인원·총 장비가치·HP 등. **그래프 기반 거리로 공간 특징**을 만들어 사용. **장비·잔여 HP가 가장 중요한 특징**이라고 보고.
- 파생: **ESTA 데이터셋**(arXiv 2209.09861, 프로 CS:GO 1,558경기 로그 + 승률 벤치마크), **"Optimal Team Economic Decisions in CS"**(arXiv 2109.12990, 점수·장비·돈으로 게임 단위 승률 → 소비 결정).
- **우리 관련:** 우리 `outcome-predictor`·`ROUND_VALUE_MODEL.md`와 직결. 공간 특징을 **싸게(그래프 거리)** 넣는 법, 경제 결정을 승률로 다루는 법은 우리 세이브/바이 엔진의 근거가 된다. **장비·HP·인원이 지배적 특징**이라는 점은 저사양 모델 설계(무거운 위치 특징 없이도 잘 맞음)에 유리.
- 신뢰도: A(논문).

### C.3 VALORANT 성과 지표 (업계 표준)

- **KAST**(라운드 중 킬/어시/생존/트레이드 비율), **ADR**(+ 킬 기여분을 뺀 조정판 ADRa), **FK/FD**(오프닝 듀얼, 트레이드 창 안에 되죽으면 "트레이드됨"), **클러치**(1vX 승리), **VLR 합성 레이팅**(약한 바이에서의 킬에 가중, 트레이드 보정, 어시·생존 포함).
- **우리 관련:** 이 지표들은 **이미 우리 데이터에 들어와 있다** — `docs/research/PLAYER_RATINGS.md`가 VCT Reference에서 ACS·ADR·KAST·HS%·FK/FD·멀티킬·클러치를 받아 선수 능력치로 변환. 다만 **엔진이 경기 후에 이 지표를 재생산/표시하지는 않는다**(검증·관전 양쪽에서 빠짐).
- 신뢰도: B(커뮤니티/매체 정의), 매핑은 우리 내부 문서 A.

### C.4 GRID Riot Open Access (공식 데이터)

- 무료 API 키로 공식 LoL·VALORANT e스포츠 데이터 제공(학생·연구자·취미·초기 개발자, **비상업·지연 데이터**). Central Data Feed + Series State API(Loopfeed), 과거 데이터.
- **우리 관련:** `docs/research/GRID_ACCESS.md`에 이미 조사됨 — VALORANT 피드는 **라운드 경제·스킬/궁극·스파이크 이벤트·로드아웃·클러치 확률·픽**은 주지만 **10인 시점별 위치(per-tick 좌표)는 공개 설명에 없음**. 상업화 시 별도 유료 라이선스.
- **판단:** 위치 데이터가 없으므로 "공간 시뮬 학습용"으론 한계. 그러나 **경제·클러치·픽 분포 검증용**으론 합법적 1차 소스. 신청은 사용자 판단 사항(미신청).
- 신뢰도: A(공식), 위치 부재는 "확인 필요"로 남김.

## D. 저사양 렌더링 사례 (감독 게임의 2D 경기 뷰)

- **FM**: 하이라이트 양 선택(전체→키), 2D 전용 시 그래픽 Low, 60hz 제한 — **결정적 순간만 그리고 나머지는 결과로 건너뛴다**가 핵심.
- **OOTP**: 아예 텍스트/박스스코어 중심, 렌더 자체가 선택적. 상세도·저장량을 사용자가 조절.
- **공통 원리:** 경기의 모든 틱을 그릴 필요가 없다. **(1) 이벤트(킬·설치·해체·클러치)만 렌더**, (2) 나머지는 즉시 결과, (3) 렌더 품질·FPS를 프리셋으로.
- **우리 현황:** 매치 스크린은 `matchday/timeline.ts`가 라운드를 **연속 이동으로 복원해 전부 재생**한다. "즉시 결과"(건너뛰기)와 "전부 관전" 양 극단만 있고, **그 사이의 "키 하이라이트만"이 없다.** 이게 저사양 원칙과 가장 어긋나는 지점이다.
